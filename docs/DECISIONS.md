# Decisions

| Date | Decision | Why | Alternative not taken |
|---|---|---|---|
| 2026-10-17 | Extract the deployment discipline from Slotback into a kit, then prove it with a second deployment | One deployment shows it can be done; a repeatable one shows it scales | Building a second project from scratch |
| 2026-10-17 | Two packages: `voiceledger` (standalone verifier) and `voiceops` (the kit) | An auditor must verify a ledger without installing a web stack | One package with extras |
| 2026-10-17 | Ledger checks become pluggable generic rules (`requires_before`, `follows_snapshot_order`, `always_followed_by`, `never`) | Slotback's two domain checks are instances of general patterns other use cases need | Hard-coded checks per project |
| 2026-10-17 | One project contract file, `voiceops.toml` | Every command reads the same declared setup; nothing hidden in constants | Per-command flags |
| 2026-10-17 | Safety prompt fragments ship as defaults that can be reworded but not dropped without a logged reason | Safety shouldn't depend on remembering to copy it | Optional examples |
| 2026-10-17 | Scope: ElevenLabs only in v1, behind adapter modules | Depth over breadth; adapters keep the door open | Multi-platform from the start |
| 2026-10-17 | Acceptance = Slotback migrated with no behaviour change, then a new use case live in ≤ 3 working days | Measurable, not "it feels reusable" | Feature checklist |
| 2026-10-17 | Keep the ledger's v1 wire format byte-identical: event fields (incl. `slot_id` as the subject key), the `slotledger-head` signing tag, bundle member names | Any rename changes every hash and signature, so existing signed bundles (Slotback's evidence) would stop verifying | Generic names with a migration tool |
| 2026-10-17 | Event-type allow-list is optional (`types=` on `seal` / `record_and_apply`), not built into the ledger | The set of event types is domain knowledge; Slotback passes its own list | A kit-wide event vocabulary |
| 2026-10-17 | `follows_snapshot_order` takes explicit `ranked`, `advance_on`, `claim`, `fill` (with payload matchers) rather than a single `event` | Slotback's list-order check depends on which events close a rank (e.g. `call_attempt` with outcome `busy`); a shorter config couldn't reproduce it | Hard-coding Slotback's rank lifecycle |
| 2026-10-17 | Rule check details are generic wording; status and failing seq are the parity contract | Same result on 403 mutated copies of the showcase bundle (status + seq per check) vs Slotback's verifier | Per-rule message templates to copy Slotback's wording |
| 2026-10-17 | Kit safety is seven named slots (§4.4). A project rewords a slot by mapping it to its own fragment; unmapped slots get the kit default appended; dropping one needs `allow_remove` with a reason. The build writes `safety.json` saying how each slot was met per profile | Safety can be reworded for a domain and language but never disappears silently, and a reviewer can see why from one file | Checking for required fragment names only (Slotback's approach), which can't tell a reworded rule from a missing one |
| 2026-10-17 | Domain safety rules (e.g. Slotback's no-clinical-advice) stay project fragments, listed in `required_fragments` | They aren't general enough to be kit defaults, but still must be in every profile | Making every project rule a kit slot |
| 2026-10-17 | Kit defaults are appended after the project's fragments, not prepended | Prompt reads role, task, then rules; position doesn't change what's spoken first (the first message does) | Prepending safety before the role |
| 2026-10-17 | A tool parameter without a description fails the build | The platform rejects it at push time; failing at build moves the error to CI | Leaving it to a project test |
| 2026-10-17 | The call-token store works on a project's existing calls table (column names configurable, extra columns returned with the token), or on its own `call_tokens` table | Slotback keeps tokens on its domain `calls` table and binds inside the ledger transaction; a separate table would mean a schema migration and a second write | A kit-owned token table only |
| 2026-10-17 | `bind` refuses to rebind a call already bound to a different subject | Defence in depth: the domain code already checks, but the store shouldn't allow it either | Unconditional update, as before |
| 2026-10-17 | Guard checks are FastAPI dependencies, so they run before the body is validated | An unauthenticated request with a bad body gets 401, not a 422 that describes the tool's schema. This is the one intended behaviour change for Slotback | Checks inside the endpoint (Slotback's original) |
| 2026-10-17 | `secret_matches` compares bytes and refuses empty secrets | `hmac.compare_digest` on non-ASCII `str` raises TypeError (a 500); an unset secret must never accept an empty header | Comparing `str` directly |
| 2026-10-17 | The leak detector's vocabulary is a project TOML file: labelled terms, named regex patterns, and rules whose regexes must all match | Detection logic is generic; what counts as protected detail (specialties, balances, claim numbers) is per project and per language | Subclassing a detector in code |
| 2026-10-17 | When the leak detector fails its known-answer set, the report's `privacy_leaks` is `null` (unproven), not a number | A count from a detector that misses planted leaks would read as "0 leaks" | Reporting the count anyway next to a FAIL |
| 2026-10-17 | `privacy_leaks` counts any scenario whose leak check is false, at tool and conversation level (`[evals] leak_checks`) | Slotback counted only the tool-level check, so a leaking conversation would not have been counted | One fixed check name |
| 2026-10-17 | Projects plug into the gate with three hooks: a scenario list, a tool-runner context manager, a conversation-setup factory | Database setup, sessions and personas are domain code; the gate, scoring and report are the kit's | A config-only gate |
| 2026-10-17 | Deploy checks are declared in `[[deploy.checks]]` (six kinds), with `env:NAME` for secrets and URLs | A new project lists what "deployed" means for it; no copied script | A script per project |
| 2026-10-17 | A network error is a FAIL line, and the timeout is configurable (default 30 s) | Slotback's script crashed with a traceback when its free instance was waking up | Letting exceptions surface |
| 2026-10-17 | The review sheet is rendered from the platform's raw conversation, with automatic checks (disclosure, verification, leak detector, tool errors, promises no tool backs, who ended the call) and a findings table pre-filled from them | Call 02's hand review found an invented "email confirmation"; the sheet now flags it automatically, so the reviewer starts from the evidence | Hand-written review pages only |
| 2026-10-17 | Phone numbers never reach a review sheet (last three digits only); raw conversations and audio stay in a gitignored folder, and `fetch` warns if it isn't | The raw conversation holds the caller's real number | Redacting by hand before sharing |
| 2026-10-17 | The `init` template is a working, domain-neutral "case line" with an in-memory store (`MemoryTokenStore`, in-memory ledger) | It must pass its own gate, tests and lint from scratch with no database and no platform account; the domain is the part a project replaces | An empty skeleton, or a template that needs Postgres to start |
| 2026-10-17 | The template declares tool-level scenarios only; conversation scenarios are written but added to the gate when the agent is pushed | A gate that included them would be ERRORED from day one; hiding them behind an environment check would let the gate pass by not running them | Including them (always ERRORED) or skipping them silently |
| 2026-10-17 | A profile can override its direction's `first_message` | A no-recording profile must not say "this call is recorded" (Slotback's production-reference profiles did) | One first message per direction only |
| 2026-10-17 | `examples/case-line` is committed `init` output, and a test fails if it drifts from a fresh `init` | The example is what a new project gets, never a hand-tuned showcase | A separate hand-written example |
| 2026-10-17 | Slotback migrated on a branch, one commit per module, each green on Slotback's own CI steps; one behaviour fix (no recording notice on profiles that don't record) in a separate commit after parity | Each commit shows one module's parity on its own; the fix isn't hidden inside a "no behaviour change" commit | One big migration commit |
| 2026-10-17 | The migration branch depends on the kit by local path and merges after voiceops is published | Slotback's CI and its container install dependencies from a public source; vendoring kit code into Slotback would defeat S3 | Vendoring, or merging with a path that only works on one machine |
| 2026-10-17 | `push` adopts or cleans up a workspace tool only if it calls this deployment's own endpoint, never by name alone | A second project in the same ElevenLabs workspace has tools with the same names (`log_outcome`, `transfer_to_human`); matching by name would repoint or delete the first project's live tools | Matching by tool name (Slotback's original, safe only with one project per workspace) |
| 2026-10-17 | Known platform constraints fail the build, not the push: an English agent needs an English TTS model; a placeholder voice can't be pushed | Found pushing the second deployment: the platform refused a multilingual model for an English agent. CI is the cheaper place to learn it | Letting the push fail |
| 2026-10-17 | The conversation gate checks `forbidden_phrases` on every agent turn, deterministically, and the kit's handoff fragment forbids claiming a transfer when the tool books a callback | The second deployment's first conversation run: the agent said "I'm connecting you to someone right now" and the platform's judge passed it | Relying on the judge |
| 2026-10-17 | The `init` template matches dates and references as callers say them (`normalise_date`, `alnum`) | All three conversations in that run failed identity with the right details: the agent passed the date on in another format and the service compared strings exactly | Exact string comparison, or a strict date type that makes the agent retry |
